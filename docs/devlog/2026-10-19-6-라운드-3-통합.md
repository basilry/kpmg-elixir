## 결정과 트레이드오프

- **C-07 은 새 함수 대신 `count_findings/2` 를 넓혔다.** 대안은 실행 요약 전용 함수(`run_summary/2` 등)였다. `count_findings/2` 는 이미 S4 탭 숫자에 쓰고, Ecto `filter/2` 로 칸 하나를 더하면 쿼리 수가 그대로다. 반환 맵에 키가 하나 늘어서 S4 기본값과 기존 테스트도 같이 고쳤다.
- **S2 실행 표의 룰 열은 실패한 룰도 끝난 룰로 센다.** S4 진행 요약(`test_progress/1`)이 이미 그렇게 센다. 화면설계서 S2.2 상태 변형은 일부 실패를 "7 / 8" 로 그렸지만, 같은 실행이 S2 에서 7 / 8, S4 에서 8 / 8 로 보이는 것이 더 헷갈린다고 봤다. 실패 여부는 상태 열("일부 실패")이 따로 보여준다. 화면설계서 S2 영역 8 비고에 적었다.
- **S1 은 실시간이 아니다.** 화면설계서 S1.3 대로 아무 토픽도 구독하지 않고 mount 때 한 번 읽는다. 감사 대상이 많아도 토픽 수가 늘지 않는다. 대신 목록을 다시 열어야 최신 상태가 보인다.
- **단추를 숨겨도 서버 검사는 그대로 둔다.** 화면은 실행 중인 GL 의 단추를 숨기지만, 다른 탭에서 동시에 누르는 경우는 `start_test_run/3` 의 `:run_in_progress` 가 막는다. 이 오류와 `:import_not_ready`, `:forbidden` 은 각각 한국어 flash 로 바꿨고 changeset 오류는 내부 내용을 보이지 않는 일반 문구로 둔다.
- **D 의 오탐은 메인이 고치지 않고 D 에게 돌려보냈다.** `anthropic.ex` 는 D 소유 파일이고, 메인이 고치면 D 의 테스트와 devlog 가 실제 코드와 어긋난다. 대신 통과/거절 문장 목록을 계약처럼 넘겨 판단 기준을 메인이 정했다.

## 막힌 점과 해결

- **스트림 행을 테스트가 못 찾았다.** `stream(:test_runs, ...)` 의 기본 dom_id 는 `"test_runs-<id>"` 다(스트림 이름 그대로). 화면설계서의 id 규칙은 하이픈이라 `stream/4` 에 `dom_id: &"test-runs-#{&1.id}"` 를 줬다.
- **약한 단언 두 개.** "2 / 1" 이 맞게 나온 것은 fixture 의 `rule_count` 기본값 때문이었다. `finished_run/3` 이 `rule_count: 2` 를 넘기게 고쳤다. 검토자에게 행동 열이 없음을 확인하는 `refute` 가 `#imports th` 를 봤는데 `#imports` 는 tbody 라 언제나 통과했다. `#imports-section th` 로 고쳤다.
- **임의 id 브로드캐스트.** 기존 "다른 토픽 메시지" 테스트가 아무 id 로 `test_run_updated` 를 보냈다. 이제 핸들러가 `get_test_run!` 을 부르므로 프로세스가 죽는다. 그 테스트에서 빼고, 실제 실행으로 다시 그리는 경우를 새 테스트로 덮었다.
- **승인 발견을 공용 setup 에 넣으면 다른 목록 테스트가 깨졌다.** 승인 개수 테스트를 따로 만들어 그 안에서만 넣었다.
- **Orca 터미널.** 세 가지가 있었다.
  - 워커 A 의 첫 실행에서 프롬프트가 전달되지 않아 다시 띄웠다.
  - `git worktree add` 로 만든 worktree 의 터미널은 Orca 에 등록되지 않아 `orphaned` 로 남고 화면에 안 보였다. `orca worktree create` 로 만들고 `--worktree name:` 으로 띄우도록 CLAUDE.md 에 적었다(801d680).
  - `terminal_worktree_mismatch` 는 `--worktree path:` 를 줘서 풀었다.

- **정답 라벨 시험의 간헐 timeout.** A 병합 뒤 라운드 4 선행 작업 중 전체 실행에서 `RulesLabelTest` 2건이 15초 timeout 으로 실패했다 (387/389, 36.8초). 단독으로 돌리면 4.8초에 통과했고 다시 전체를 돌리면 389 passed 였다. DB 에 남은 행이나 다른 활동은 없었다. `DuplicateEntry` 의 그룹 쿼리가 부하가 걸린 DB 에서 느려지는 것으로 보고, 원인 조사 (EXPLAIN ANALYZE) 는 라운드 4 W5 에 맡겼다.

## Elixir 학습 포인트

- **LiveView 스트림은 서버에 행을 남기지 않는다.** 렌더한 뒤 행 데이터는 클라이언트 DOM 에만 있다. 그래서 다른 assign(`running_import_ids`) 이 바뀌어도 이미 그린 적재 행의 단추는 저절로 바뀌지 않는다. 같은 항목을 `stream_insert/3` 로 다시 넣으면 같은 dom_id 의 행이 그 자리에서 바뀐다. 실행 행은 `at: 0` 으로 넣어 새 실행이 위에 온다.
- **스트림 항목은 스키마가 아니어도 된다.** `%{id: ..., run: ..., done: ..., review_queue: ...}` 처럼 `:id` 가 있는 맵이면 된다. 행마다 미리 계산한 값을 들고 다니게 해서 템플릿에서 쿼리를 하지 않는다.
- **HEEx `:let` 은 컴포넌트와 슬롯에만 쓴다.** `<tr :let={...}>` 는 컴파일 오류다. 행마다 계산이 필요하면 헬퍼 함수(`summary_for/2`) 를 부른다. `:if`, `:for` 는 일반 태그에도 된다.
- **Ecto `filter/2` 집계.** `filter(count(f.id), f.score >= ^threshold and f.status == :approved)` 는 SQL `COUNT(...) FILTER (WHERE ...)` 가 된다. 한 번의 쿼리로 검토 큐, 경미, 승인 세 칸을 센다.
- **`DISTINCT ON` 으로 그룹별 최신 행.** `distinct: r.engagement_id, order_by: [desc: r.started_at, desc: r.id]` 는 감사 대상마다 가장 최근 실행 한 건을 고른다. Ecto 가 distinct 열을 ORDER BY 맨 앞에 넣어 주므로 `order_by` 에는 "무엇이 최신인가" 만 쓴다. `r.id` 는 같은 시각일 때 결과를 고정한다. PostgreSQL 전용 기능이다.
