## 결정과 트레이드오프

- **`ai_triages.model` 은 요청 모델, 유일 키에 들어간다.** 대안은 응답 모델 (`response_model`) 을 키로 쓰는 것이었다. 응답 모델은 API 를 부른 뒤에야 알 수 있어서, "같은 입력이면 API 를 다시 부르지 않는다" 는 재사용 검사를 호출 전에 할 수 없다. 그래서 클라이언트가 요청할 모델을 알려주는 `model/0` 을 만들었다. Fake 와 실제 모델의 제안이 같은 키로 섞이지 않는 효과도 있다.
- **일괄 요청은 조건부 `update_all` 로 중복을 막는다.** 대안은 후보 finding 을 모두 `FOR UPDATE` 로 잠그는 것이었다. 100건을 잠그면 건별 요청이나 워커 완료와 잠금 순서가 엇갈릴 수 있다. `where triage_status == :none` 를 update 에 다시 걸고 실제로 바뀐 id 만 job 으로 넣으면, 동시 요청이 와도 한 finding 은 한 번만 들어간다. 대가는 후보를 고른 뒤 다른 요청이 가져간 건은 조용히 빠진다는 점이고, 반환하는 `enqueued` 가 실제 수를 알려준다.
- **일괄 요청은 finding 마다 broadcast 하지 않는다.** `:triage_requested` 한 번을 보내고 S4 가 한 번 다시 읽는다. 대안 (finding 마다 `finding_updated`) 은 100번 다시 읽게 된다.
- **`decide/4` 가 `conclusion_id` 를 받는다 (C-11).** 검토자가 화면을 연 뒤 작성자가 결론을 다시 내면, 검토자는 보지 않은 결론을 승인하게 된다. 화면이 본 결론 id 를 넘기고 최신 결론과 다르면 `:stale` 로 막는다.
- **작성자의 검토 시도도 `review.denied` 로 남긴다 (C-10).** 비멤버는 이벤트 없이 `:forbidden` 이다. 비멤버에게 이벤트를 남기면 그 감사 대상의 로그에 외부인이 흔적을 쓸 수 있고, 대상의 존재를 알려주게 된다.
- **S6 전표번호 필터는 payload 의 `entry_number` 로 거른다 (C-13).** 화면설계서는 finding 을 거쳐 찾는 서브쿼리를 제안했다. 그러면 `AuditTrail` 이 Testing 테이블을 알아야 한다. finding 대상 이벤트가 모두 `entry_number` 를 갖게 하면 `AuditTrail` 은 다른 컨텍스트에 기대지 않는다. 대가는 payload 키 규칙을 모든 컨텍스트가 지켜야 한다는 점이고, 4.2 표에 적었다.
- **`ai_triage.failed` 의 행위자는 system.** 재시도 소진이나 크래시에는 모델 응답이 없다. 실패를 판정하는 쪽은 워커다.
- **화면 동작은 라운드 4b 로 미뤘다.** S5 의 단추와 S4 의 AI 열을 지금 같이 맡기면 W4 는 아직 없는 Triage, Review 함수를 흉내 내야 한다. 시그니처가 바뀌면 다시 고쳐야 한다. 대신 읽기 화면만 먼저 만들게 했다.
- **워커 5명.** AGENTS.md 5.4절의 3-4명 상한을 넘는다. 사용자 지시를 따랐고, W5 는 파일이 겹치지 않는 마무리 작업이라 검토 부담이 작다고 봤다.

## Elixir 학습 포인트

- **behaviour 콜백을 늘리면 모든 구현이 컴파일 경고를 낸다.** `@callback model/0` 을 추가하자 `@impl true` 가 없는 구현은 "required by behaviour" 경고를 낸다. `mix precommit` 은 경고를 오류로 다루므로 Fake 와 Anthropic 을 함께 고쳐야 통과한다. 계약 변경이 구현 누락을 컴파일 단계에서 잡아준다.
- **LiveView 의 `handle_info/2` 는 처리하지 않는 메시지에서 죽는다.** 같은 토픽을 여러 화면이 구독하므로, 한 화면에만 필요한 메시지를 추가하면 나머지 화면에 무시 절을 넣어야 한다. 마지막에 `def handle_info(_, socket)` 를 두는 방법도 있지만, 그러면 메시지 이름을 잘못 쓴 버그도 조용히 묻힌다. 메시지마다 절을 두었다.
