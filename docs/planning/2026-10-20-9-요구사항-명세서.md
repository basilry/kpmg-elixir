## 1. 목적과 범위

Tickmark는 감사인과 AI가 협업하는 감사 Work OS의 축소판이다. 첫 업무인 분개 테스트에서 의심 전표를 선별하고, AI 제안과 사람의 결론 및 검토를 연결해 판단 근거를 추적하는 것이 목적이다. 이 문서는 무엇을 제공해야 하는지와 기준 커밋에서 어디까지 구현했는지를 구분한다. 사용자 동작과 처리 순서는 기능 정의서에 둔다.

MVP는 감사 대상 생성, 멤버 추가, 합성 GL 적재, 룰 8종 실행, AI 트리아지 요청, 작성자 결론, 검토자 승인 또는 반려, 감사 로그 조회까지다. AI는 제안만 하고 판단과 서명은 사람이 한다. 제품 전체 성공 조건은 3분 시연, `mix precommit` 통과, 외부 데모 URL 및 README 제공이다. 구현 코드가 있다는 사실과 시연 및 배포 완료는 별개다. 근거: MVP 1-3, 7장, WBS M0-M6.

## 2. 용어와 ID 체계

| 용어 | 뜻과 코드 대응 |
|---|---|
| 감사 대상 | 회사와 회계연도로 구분하는 `engagement`; 권한과 데이터 경계 |
| GL / 전표 / 행 | 총계정원장 파일 / `journal_entries` / `journal_lines`; 같은 전표번호의 행들을 묶음 |
| 적재 | `ledger_imports`: `pending`, `processing`, `succeeded`, `failed` |
| 테스트 실행 | `test_runs`: `running`, `completed`, `completed_with_errors`; 룰별 상태는 `queued`, `running`, `succeeded`, `skipped`, `failed` |
| 검토 항목 | `finding`: 한 실행에서 적중한 전표 1건; 전표의 부정 확정을 뜻하지 않음 |
| 룰 점수 / 검토 큐 | 적중 가중치 합의 상한 100 / 실행에 저장한 `triage_threshold` 이상인 항목; 기본 25 |
| AI 제안 | `ai_triages`; `triage_status`는 `none`, `queued`, `succeeded`, `failed`; 사람 상태와 독립 |
| 사람 결론 | `conclusions.outcome`: `no_exception`(이상 없음), `needs_follow_up`(추가 확인 필요), `exception`(예외) |
| 검토 상태 | `findings.status`: `open`, `concluded`, `approved`, `rejected`; `review_decisions.decision`은 `approved`, `rejected` |
| 직무 분리 | 결론 작성자와 검토자가 달라야 함; 역할 변경 이력이 있어도 자기 결론 검토 금지 |
| 감사 이벤트 | `audit_events`; 실제 action과 행위자 유형 `user`, `agent`, `system`을 저장; `seq`는 정렬용 DB 부여 값이며 결번 없음은 보장하지 않음 |

근거: 계약 3-5, 8장; `lib/tickmark/testing/{test_run,finding}.ex`, `lib/tickmark/review/{conclusion,review_decision}.ex`, `lib/tickmark/audit_trail/audit_event.ex`. 함수 표기의 `Engagements`, `Ledger`, `Testing`, `Triage`, `Review`, `AuditTrail`, `AI`, `Accounts`는 모두 `Tickmark` 아래 모듈이다.

| ID | 의미 | 규칙 |
|---|---|---|
| `REQ-{영역}-{nn}` | 기능 요구사항 | ACC, ENG, GL, RUN, AI, REV, AUD, UI; 영역 안에서 순번 |
| `NFR-{nn}` | 비기능 요구사항 | 문서 전체 순번 |
| `FN-{영역}-{nn}` | 기능 정의 | S1-S6, AUTH, SYS; 기능 정의서 참조 |
| S1-S6 | 화면 | 목록, 감사 대상 상세, GL 불러오기, 테스트 실행, 전표 검토, 감사 로그 |
| WBS `n.n` | 작업 분해 항목 | WBS 문서의 기존 번호를 그대로 사용 |

ID 근거는 계약 12.4다. 표의 문서 약칭은 머리의 관련 문서 링크를 가리킨다. 코드 경로와 테스트 경로는 저장소 상대 경로다.

| 상태 | 이 문서에서의 의미 |
|---|---|
| 구현 | 기준 커밋에 코드와 관련 테스트가 있음. 이번 문서 작업에서 테스트를 재실행했다는 뜻은 아님 |
| 부분 | 백엔드 또는 일부 화면만 있음 |
| 미구현 | 계획만 있고 해당 동작을 제공하지 않음 |
| 진행 중 | 기준 커밋에서는 미완료이고 W6, F1, F2에 배정됨. 향후 브랜치 결과를 현재 사실로 포함하지 않음 |
| 확인 필요 | 소스만으로 결과를 확정할 수 없거나 통합·운영 검증이 남음 |

우선순위는 MVP 필수, MVP 선택, 2단계로 구분한다. 별도 성능 SLA나 보안 인증 기준은 합의되지 않았으므로 임의의 목표치를 만들지 않는다.

## 3. 이해관계자와 역할

| 이해관계자 | 책임과 기대 |
|---|---|
| 작성자 (`preparer`) | GL과 룰 결과, AI 제안을 검토하고 자기 결론 및 코멘트를 제출 |
| 검토자 (`reviewer`) | 최신 결론과 증거를 읽고 승인하거나 사유를 붙여 반려 |
| 감사 대상 생성자 | 생성 시 작성자 멤버가 되며 이미 가입한 사용자를 멤버로 추가 |
| AI (`agent`) | 위험도와 추가 절차만 제안. 사용자 멤버 역할이 아님 |
| 시스템 (`system`) | 적재, 룰, 트리아지 잡 수행 및 감사 기록. 사용자 역할이 아님 |
| 개발자 / 포트폴리오 평가자 | 요구사항, 구현 근거, 테스트, 미완료 범위를 추적 |

### 실제 권한표

| 권한 / 행동 | `preparer` | `reviewer` | 비멤버 | 검사 위치 |
|---|---|---|---|---|
| S1 목록 및 신규 생성 | 로그인하면 가능 | 로그인하면 가능 | 로그인하면 가능 | `UserAuth`, `Engagements.list_engagements/1`, `create_engagement/2` |
| `:view` | 허용 | 허용 | 거부 | `Engagements.authorize/3` |
| `:import_ledger` | 허용 | 거부 | 거부 | `Policy.allowed?/2`, Ledger |
| `:start_test_run` | 허용 | 거부 | 거부 | `Policy.allowed?/2`, Testing.Runner |
| `:request_triage` | 허용 | 거부 | 거부 | `Policy.allowed?/2`, Triage |
| `:submit_conclusion` | 허용 | 거부 | 거부 | `Policy.allowed?/2`, Review |
| `:review_conclusion` | 거부 | 허용, 자기 결론 제외 | 거부 | `Review.decide/4`, DB CHECK 및 복합 FK |
| `:manage_members` | 생성자인 멤버만 | 생성자인 멤버만 | 거부 | Policy는 모두 false; `Engagements.authorize/3`의 별도 생성자 검사 |
| 정의하지 않은 권한 | 거부 | 거부 | 거부 | `Policy.allowed?/2`의 기본 false |

근거: `lib/tickmark/engagements/policy.ex:10`, `Engagements.authorize/3`; `test/tickmark/engagements/policy_test.exs`, `authorization_test.exs`. 생성자는 별도 역할명이 아니며 기본 생성 흐름에서는 `preparer`다. 한 감사 대상에서 한 사용자는 하나의 역할만 가지며 `(engagement_id, user_id)` unique 제약이 중복을 막는다.

직무 분리는 화면 버튼, context, DB에서 나누어 보장한다. 승인·반려는 `concluded`에만 가능하고 화면에서 본 `conclusion_id`가 최신이어야 한다. `Review.decide/4`는 권한, finding 잠금 및 상태, 최신 결론, 자기 검토 순으로 검사한다. 작성자 역할의 검토 시도는 `review.denied`의 `reason=role`, 과거 자기 결론을 가진 검토자의 시도는 `reason=self_review`다. 비멤버의 시도는 감사 대상을 오염시키지 않도록 기록하지 않는다. DB의 `reviewer_not_preparer` CHECK와 `(conclusion_id, preparer_id)` 복합 FK가 우회를 막는다. 근거: 계약 8장, `lib/tickmark/review.ex`, `priv/repo/migrations/20261017110531_create_review.exs`, `test/tickmark/review_test.exs`.
