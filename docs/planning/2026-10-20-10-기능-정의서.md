## 1. 목적과 범위

이 문서는 감사 대상 생성부터 GL 적재, 룰 실행, AI 제안, 사람의 결론과 검토, 감사 로그까지 각 동작이 어떻게 처리되는지 정의한다. 요구사항의 이유·수락 기준·WBS 추적은 요구사항 명세서를 참조한다. 한 기능은 하나의 사용자 동작 또는 독립된 시스템 처리 단위다. 룰 8종은 사용자가 함께 실행하는 하나의 시스템 기능 안에 정의한다.

기준 커밋에서 동작하는 내용과 후속 연결 계획을 분리한다. `구현`은 코드와 관련 테스트 존재, `부분`은 일부 계층만 구현, `미구현`은 계획만 존재, `진행 중`은 W6/F1/F2 배정, `확인 필요`는 검증 근거 부족을 뜻한다. 이번 작업에서는 애플리케이션 테스트·브라우저·외부 API·배포를 실행하지 않고 코드와 기존 테스트를 읽었다. 이 문서의 테스트 경로는 실행 성공 보고가 아니다.

실제 고객 데이터·ERP 연동·다중 통화·외부 메일 인프라와 2단계 기능은 MVP 동작에 포함하지 않는다. 합성 데이터만 사용한다. AI는 제안하며 사람의 `finding.status`를 변경하지 않는다. 근거: MVP 2-4장, 계약 2, 7, 8장.

## 3. 공통 처리 규칙과 입력 계약

### 3.1 권한, 트랜잭션, 오류

- 역할은 실제 코드의 `preparer`, `reviewer` 두 가지다. 생성자는 별도 역할이 아니며 생성 시 preparer가 된다. 멤버 추가는 역할표와 별개로 생성자인 멤버만 가능하다.
- S1-S6은 HTTP의 `require_authenticated_user`와 LiveView의 `:require_authenticated`를 거친다. S2-S6 상세는 비멤버·없는 ID·잘못된 UUID를 같은 404로 처리한다. 기준 404 본문은 `Not Found`이며 한국어 안내는 F1 진행 중이다.
- 화면 숨김·disabled는 편의 장치다. 변경 함수는 scope로 권한을 다시 검사하고, S2/S4/S5는 URL의 감사 대상과 자식 데이터 소속도 확인한다.
- 업무 변경·이벤트·잡 등록은 해당 Ecto.Multi 또는 Repo.transact에서 함께 처리한다. PubSub는 커밋 뒤 전송한다. 단순 조회와 폼 검증에는 트랜잭션·잡·감사 기록이 없다.
- `:forbidden` 등은 함수 오류 코드다. 화면에는 해당 기능의 고정 문구를 보인다. 아직 연결되지 않은 기능은 목표 문구라고 명시한다.

근거: `Engagements.authorize/3`, `lib/tickmark/engagements/policy.ex`, `lib/tickmark_web/user_auth.ex`, 계약 2, 4, 6, 8장; `test/tickmark/engagements/authorization_test.exs`, `test/tickmark_web/engagement_routes_test.exs`.

### 3.2 GL 입력 필드

FN-S3-01과 FN-SYS-01이 함께 사용하는 실제 계약이다. 헤더 16개는 모두 존재해야 하며 순서는 자유다. UTF-8, BOM, CRLF, 따옴표 안 쉼표·줄바꿈을 지원한다. 완전히 빈 레코드는 건너뛴다. 헤더만 있는 CSV는 파서가 0건으로 허용하지만 크기 0인 파일은 적재 등록 changeset에서 거부한다.

| 필드 | 형식·검증 | 실패 코드 |
|---|---|---|
| entry_number | 필수 문자열, 최대 200자, 같은 번호 행 연속 배치 | required, too_long, non_contiguous_entry |
| line_number | 정수 1-999999, 전표 내 유일 | invalid_number, duplicate_line_number |
| posting_date | YYYY-MM-DD | invalid_date |
| document_date | YYYY-MM-DD | invalid_date |
| entered_at | YYYY-MM-DD HH:MM:SS, 오프셋 없는 KST; Z와 +09:00 거부 | invalid_date |
| fiscal_year | 정수 1000-9999; 감사 대상 생성 폼의 2000-2100과 다른 제한 | invalid_number |
| fiscal_period | 정수 1-13; 13기는 기간 불일치 경고 제외 | invalid_number, period_mismatch |
| account_code | 필수 문자열, 최대 200자 | required, too_long |
| account_name | 필수 문자열, 최대 200자 | required, too_long |
| debit | 음수·지수·쉼표 금지, 원 단위 정수 또는 0 소수부; 빈 셀은 0 | invalid_number, both_sides |
| credit | debit과 동일; 행에서 두 금액 중 정확히 하나만 양수 | invalid_number, both_sides |
| description | 선택 문자열, 최대 500자 | too_long |
| counterparty | 선택 문자열, 최대 200자; 전표 헤더 일관성 검사 | too_long, inconsistent_header |
| entered_by | 필수 문자열, 최대 200자 | required, too_long |
| approved_by | 선택 문자열, 최대 200자; 수기 전표도 공란 허용 | too_long |
| source | manual 또는 system | required, invalid_value |

각 셀은 유효한 UTF-8이고 NUL이 없어야 한다. 금액의 저장 상한은 numeric(18,2)의 `9999999999999999.99`이며 정수 금액만 받으므로 허용 정수의 최대는 `9999999999999999`다. 전표 합계와 전체 차변 합계도 상한을 검사한다. posting_date, document_date, entered_at, fiscal_year, fiscal_period, entered_by, approved_by, source, counterparty는 같은 전표 안에서 같아야 한다. 근거: MVP 5장; `Tickmark.Ledger.CsvParser.parse/3`, `Tickmark.Ledger.CsvParser.Row.parse/2`; `test/tickmark/ledger/csv_parser_test.exs`.

### 3.3 S3의 실제 오류 문구

| 코드 / 조건 | 현재 문구 |
|---|---|
| missing_column | 필수 컬럼이 없습니다 |
| unknown_column | 알 수 없거나 겹친 컬럼이 있습니다 |
| required | 필수 값이 비어 있습니다 |
| too_long | 값이 너무 깁니다 |
| invalid_value | 허용되지 않는 값입니다 |
| invalid_date | 날짜 또는 일시 형식이 잘못되었습니다 |
| invalid_number | 금액은 원 단위 정수여야 합니다 |
| both_sides | 한 행에는 차변과 대변 중 하나만 있어야 합니다 |
| unbalanced_entry | 전표의 차변 합계와 대변 합계가 다릅니다 |
| inconsistent_header | 같은 전표의 헤더 값이 행마다 다릅니다 |
| non_contiguous_entry | 같은 전표의 행이 이어져 있지 않습니다 |
| duplicate_line_number | 같은 전표에 같은 라인 번호가 있습니다 |
| too_many_rows | 행 수가 상한(100,000)을 넘었습니다 |
| parse_error | CSV 형식을 읽을 수 없습니다 |
| period_mismatch | 전기일의 월과 회계기간이 다릅니다 |
| too_large / file_too_large | 20MB보다 큰 파일은 올릴 수 없습니다. |
| not_accepted | .csv 파일만 올릴 수 있습니다. |
| too_many_files | 파일은 한 번에 1개만 올릴 수 있습니다. |
| invalid_seed | 정수로 입력하세요. |

`invalid_number`는 금액 외의 정수 필드에도 사용된다. 현재 문구의 한계는 12장에 남긴다. 오류에는 CSV 원래 값이나 알 수 없는 헤더를 다시 넣지 않는다. 근거: `lib/tickmark_web/live/import_live/{new,components}.ex`, 화면 S3.5와 부록 A; `test/tickmark_web/live/import_live_test.exs`.

## 4. AUTH: 계정과 인증

인증 기능은 감사 대상 역할과 무관하다. 아래 영어 문구는 기준 커밋의 실제 값이며 F2 한글화 이후 다시 확인해야 한다. 외부 이메일 전달 성공을 보장하지 않으며 현재 메일은 Swoosh Local에 저장한다 (`config/config.exs`).

### FN-AUTH-01 회원가입

| 항목 | 정의 |
|---|---|
| ID | FN-AUTH-01 |
| 이름 | 회원가입 |
| 화면과 경로 | AUTH `/users/register` |
| 행위자와 권한 | 비로그인 사용자; 역할 없음 |
| 선행 조건 | 미가입 이메일 |

| 출력·flash·PubSub·감사 이벤트 | `An email was sent to {email}, please access it to confirm your account.` 후 `/users/log-in`; 로그인 지시 메일, 감사 없음 |
| 예외와 오류 처리 | changeset 오류는 폼 유지; 이미 로그인했으면 signed_in_path로 이동 |
| 관련 REQ | REQ-ACC-01, REQ-UI-04 |
| 구현 상태 | 구현; 한글화 진행 중 F2 |

처리 흐름:

1. `Accounts.change_user_email/3`으로 입력을 검증하고 저장 시 `Accounts.register_user/1`을 호출한다.
2. 계정 저장 뒤 `Accounts.deliver_login_instructions/2`로 로그인 토큰과 메일을 만든다. 계정 insert와 메일 전송을 하나의 트랜잭션으로 묶지는 않는다.
3. 안내 flash와 로그인 화면 이동을 적용한다. 업무 Oban 잡과 감사 이벤트는 만들지 않는다.

| 항목 | 정의 |
|---|---|
| ID | FN-AUTH-03 |
| 이름 | 매직 링크 확인 및 로그인 |
| 화면과 경로 | AUTH GET `/users/log-in/:token`, POST `/users/log-in` |

| 예외와 오류 처리 | 화면 토큰 실패 `Magic link is invalid or it has expired.`, POST의 미존재·만료 토큰 실패 `The link is invalid or it has expired.` 후 로그인 이동 |
| 관련 REQ | REQ-ACC-02 |
| 구현 상태 | 구현; 한글화 진행 중 F2 |

처리 흐름:

1. `Accounts.get_user_by_magic_link_token/1`으로 GET 토큰을 확인하고 확인 폼을 보여 준다.
2. 확인 제출을 POST로 넘겨 `Accounts.login_user_by_magic_link/1`을 호출한다. 미확인 계정은 확인·기존 토큰 삭제, 확인된 계정은 사용한 토큰 삭제를 수행한다.
3. `UserAuth.disconnect_sessions/1` 및 `UserAuth.log_in_user/3`으로 세션을 정리·발급한다.
4. 저장된 복귀 경로 또는 signed_in_path로 이동한다. 기준 코드의 기본 목적지는 `/`이며 S1 연결은 FN-S1-03에서 진행 중이다.
